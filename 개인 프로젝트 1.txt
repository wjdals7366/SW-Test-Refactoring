3번째) 사용 스크립트 : bulkinsert.js, batch.js
테스트 목적 : 대량 등록된 이용권(bulk_pass, READY)을 Spring Batch {addPassesJob} 한 번으로 실제 이용권 · 예약 슬롯(pass, booking)으로 전개할 때, 건수가 늘어날수록 처리 시간이 어떻게 증가하는지 측정해 병목을 찾는 테스트

설계
- 테스트 사전 조건 : pass-project-master를 run 후 pass-batch-master를 run 한 상태
 
1단계 : 동시 등록 (VU : 20, iterations : 10000)

- k6로 가상 사용자 20명이 동시에 /admin/bulk-pass 를 호출해 신청 1만건을 적재함
- 성능 비교를 위해 100개, 200개, 400개, 10000개 케이스로 나눠서 테스트 진행

    booking.setUserId(pass.getUserId());
    // ... 상태값 설정 ...

이용권 생성 (addPasses -> addPass 개선 전)

private int addPasses(BulkPassEntity bulkPassEntity, String userId) {
    List<PassEntity> passEntities = new ArrayList<>();
    passEntities.add(PassModelMapper.INSTANCE.toPassEntity(bulkPassEntity, userId));
    return passRepository.saveAll(passEntities).size();   // 개수만 반환
}

이용권 생성 (addPasses -> addPass 개선 후)

private PassEntity addPass(BulkPassEntity bulkPassEntity, String userId) {
    PassEntity passEntity = PassModelMapper.INSTANCE.toPassEntity(bulkPassEntity, userId);
    return passRepository.save(passEntity);               // 저장된 엔티티를 반환
}

위 구문에서 쿼리 파라미터 없이 /admin으로 접속하면 400 bad request 발생
@RequestParam의 기본 값이 required = true 라서, 통계 차트 조회 기준일 to를 클라이언트가 반드시 넘겨줘야 하는 구조였음
dashboard 진입점이 외부 파라미터에 의존하는 설계기 때문에 URL을 정확히 모르면 아예 접근이 불가능한 UX 결함

@GetMapping
public ModelAndView home(ModelAndView modelAndView, @RequestParam(value = "to", required = false) String toString) {
    LocalDateTime to = (toString == null) ? LocalDateTime.now() : LocalDateTimeUtils.parseDate(toString);

변경점
1) required = true 를 required = false 로 변경해 파라미터 부재를 허용
2) toString이 없을 경우 LocalDateTime.now() 를 기본 기준일로 적용

개선 효과
1) /admin 만 입력해도 대시보드가 즉시 랜더링 됨 (UX 결함인 URL진입장벽 제거)
2) 기존기능 (날짜기준조회)은 그대로 유지 - 하위 호환성 보존
3) 사용자가 날짜를 입력하지 않더라도 오늘 기준의 통계를 보여주는 관리자 도구로서의 사용경험 개선
